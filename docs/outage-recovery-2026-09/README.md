# 2026-09-25~26 로그서버 장애 / 누락 복구 — 인수인계

작성: 2026-09-28 (서버 현지시각). 시각 표기는 멕시코 현지시각(UTC-6)이다. process-logs 파일명은 UTC 날짜다.

## 1. 장애 요약

**Oracle은 죽지 않았다.** 문제는 로그서버(20.10.30.112, APC020001)에서 DB로 가는 연결이었다.

| 근거 | 내용 |
|---|---|
| Oracle | `v$instance.startup_time` = 09-22 12:04. 이후 재시작 없음. alert log에 장애 흔적 없음 |
| MES 서버(SOLUMXSRV003) | 09-22 이후 재부팅 없음. 시스템 오류 없음 |
| DB 세션 이력 | 장애 중 로그서버 세션 대부분이 `SQL*Net break/reset to client` 대기. DB는 한가했고 클라이언트를 기다림 |
| 로그서버 | 연결 풀 대기 초과(`NJS-040`)가 수 시간 이어짐. 이후 `ENETUNREACH`, 관리자 수동 재부팅으로 정상화 |

| 시각 | 사건 |
|---|---|
| 09-25 03:20~10:40 | `NJS-040` 풀 타임아웃. INSERT 1건 약 180초. 처리량 약 1/10 |
| 09-25 10:41 | 로그서버 DNS 응답 없음, `ENETUNREACH` 약 4.6만 건 |
| 09-25 10:43 | 관리자 수동 재부팅 → 정상화 |
| 09-26 03:00~10:20 | 같은 패턴 재발 (`NJS-040` 약 7시간) |
| 09-26 10:22 | 수동 재부팅 → 10:22:51 비정상 종료 → 10:34 재기동 → 10:50 정상화 |

두 번 모두 **새벽 3시 전후에 시작**했고 로그서버 재부팅으로 풀렸다. 네트워크 장비(NAT/방화벽) 로그는 확인하지 못해서 근본 원인은 아직 확정되지 않았다.

## 3. 미완료 / 후속 작업

1. **다른 테이블 누락 점검 안 함.** LOG_EOL, LOG_ICT, LOG_REFLOW_*, LOG_FCT 등은 아직 보지 않았다. 스킬로 `collect --from 2026-09-24 --to 2026-09-27`부터 돌리면 된다. 프리셋이 없는 테이블은 SKILL.md "새 테이블 추가" 절차를 따른다.
2. **`ORACLE_CONNECT_STRING`이 외부 IP로 되어 있음.** 로그서버 `.env`가 `201.174.222.243:1588/SVEHICLEPDB`(MES 외부 IP)다. 같은 대역인 내부 IP `20.10.30.231:1588`로 바꾸는 것을 권장한다. 바꾸면 Backend 재시작이 필요하고, 사용자 승인이 필요하다.
3. **SPI-13 패드 측정 파일 수집.** 09-24부터 `IDNO._*.csv`, `69230004D1B*.csv`(헤더 없는 패드 측정값)가 들어온다. `TRG_LOG_SPI_IS_LAST`에서 `ORA-01843`/`ORA-01861`로 실패하며 약 4.6만 건 쌓였다. 검사 실적이 아니라서 재처리하지 않았다. 해결책은 둘 중 하나다.
   - 현장에서 패드 데이터 내보내기를 끈다.
   - Aggregator SPI VRL에서 첫 줄이 `MasterBarcode`가 아닌 파일을 버린다. 운영 TOML 수정 후 `POST /api/monitor/vector/reload`가 필요하다.
4. **`/api/monitor/retry`, `retry/all` 위험.** `error-log.repository.ts`의 `findByIds`/`findRetryable`/`updateStatus`가 모든 JSONL을 `readFileSync`로 읽는다. 일부 파일이 512MB를 넘는다. 날짜 범위로 좁혀 스트리밍하도록 고쳐야 한다.
5. **`docs/sql` 트리거 파일이 운영과 다름.** 예: `trg_is_last_aoi.sql`에는 운영 트리거의 IP_PRODUCT_2D_BARCODE ISCM 가드가 없다.
6. **LOG_SPI `ORA-01841` 36건.** 연도 오류로, 형식이 다른 파일로 보인다. 아직 확인하지 않았다.
7. **새벽 3시 재발 가능성.** 현지에 네트워크/방화벽 작업 일정이 있는지 확인이 필요하다. 재발하면 이 문서 1장의 방법(처리 로그 10분 단위 집계, 로그서버 이벤트 로그, `dba_hist_active_sess_history`)으로 진단한다.

## 4. 참고

- 로그서버 SSH 작업은 타임아웃을 길게 잡는다. 백그라운드 `Start-Process`는 SSH 세션이 끝나면 함께 죽는다.
- 서버 `C:\Windows\Temp`의 임시 파일은 정리했다. 스킬 스크립트는 `C:\Windows\Temp\vector-reprocess\`에 남아 있고, 재사용된다.
